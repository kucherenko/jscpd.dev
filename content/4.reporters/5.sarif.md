## Installation

The SARIF reporter is part of jscpd v5, so it needs no separate installation.

## Usage

```bash
jscpd --reporters sarif ./src
```

Output file: `./report/jscpd-report.sarif`

## GitHub Code Scanning Integration

The [jscpd GitHub Action](/ci-and-hooks/ci) writes the SARIF report and uploads it to code scanning by default (`upload-sarif: true`). To run jscpd yourself, upload the file with GitHub's `upload-sarif` action:

```yaml [.github/workflows/jscpd.yml]
name: Code duplication check
on: [push, pull_request]

jobs:
  jscpd:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      security-events: write
    steps:
      - uses: actions/checkout@v4

      - name: Run jscpd
        run: npx jscpd --reporters sarif --output ./reports .

      - name: Upload SARIF to GitHub Code Scanning
        uses: github/codeql-action/upload-sarif@v4
        with:
          sarif_file: ./reports/jscpd-report.sarif
```

Results appear in the **Security → Code Scanning** tab of your repository and as inline annotations on pull request diffs.

## Configuration

```json [.jscpd.json]
{
  "reporters": ["sarif"],
  "output": "./reports/jscpd"
}
```

## Rules

Each kind of clone has a rule of its own, so code scanning lists and filters them apart:

| Rule | Results under it |
|------|------------------|
| `jscpd/duplicate-code` | Exact copies (Type-1) |
| `jscpd/renamed-code` | Copies that match after `--ignore-identifiers`, `--ignore-literals` or `--ignore-annotations` (Type-2) |
| `jscpd/similar-code` | Copies merged across a gap of edited lines by `--max-gap-lines` (Type-3) |
| `jscpd/similar-function` | JavaScript, TypeScript and Python functions with a similar syntax-tree structure, from `--similarity` (Type-3) |
| `jscpd/semantic-code` | Functions that do the same job, from `--semantic` (Type-4, experimental) |

The report always declares `jscpd/duplicate-code`, and each other rule only when a result uses it, so a default run has one rule. A result from `--max-gap-lines`, `--similarity` or `--semantic` carries its score as the `similarity` property, and a near-miss result also has `similarity_method`, `gap` or `ast`. [Types of Code Clones](/guides/clone-types) explains each kind.

Releases up to 5.3.3 filed the pairs of `--similarity` under `jscpd/similar-code`. The first upload after an upgrade from one of them closes those alerts and opens them again under `jscpd/similar-function`.

## Severity

A result is a `warning` unless one of these makes it an `error`:

- A clone of at least N tokens, when `--sarif-error-tokens <N>` is set (config: `sarifErrorTokens`, v5.0.15+). Large duplications then fail stricter code-scanning policies, while small ones stay advisory.
- A clone that is new against the baseline of `--baseline` or `--baseline-from-ref`.
- Duplication above `--threshold`. Then every result is an `error`, matching the threshold check that fails the build.

```bash
jscpd --reporters sarif --sarif-error-tokens 150 ./src
```

## Result Identity & Related Locations (v5.0.15+)

- Each result carries a `partialFingerprints` entry (`jscpdCloneHash/v1`) plus `token_count` and `clone_hash` properties, so GitHub code scanning tracks the same clone across runs even when line numbers shift. The hash does not depend on the order of the two files, so the same clone pair gets the same fingerprint whatever order jscpd finds the files in.
- The duplicate's counterpart location has its own message (`Duplicated at <path>:<line>`), referenced from the primary message via an embedded link, so code scanning shows both sides of the clone.

## Dead code

`jscpd --dead-code -r sarif` writes `basta-report.sarif` with a rule for each category of finding, such as `unused-file` or `unused-import`. The report declares every category, even one without findings, so the last fix in a category closes its alerts. A finding's level follows its confidence: `error` from 90, `warning` from 60, and `note` below that.
